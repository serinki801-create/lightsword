 1. ВЫБРАННЫЙ ПУТЬ К KERNEL R/W — AIO KEVENT UAF (трек B, «B12»)
================================================================================

  Это единственный путь, где в репозитории уже есть ПОДТВЕРЖДЁННЫЙ на-device
  примитив. Остальные либо пропатчены в 26.2, либо без публичного PoC.

  МЕХАНИЗМ (подтверждено на устройстве, см. Documents/aio_uaf.log)
  ---------------------------------------------------------------------------
  1. Приложение (sandbox, без entitlement) открывает файл, делает aio_read
     (LIO_NOWAIT) с sigev_notify = SIGEV_KEVENT -> ядро создаёт запись
     aio_workq_entry в зоне aio_workq_zonep и вешает knote на kqueue.
  2. Второй aio_read с sigev_notify = SIGEV_NONE используется как ДОНОР:
     его запись освобождается и LIFO-claim'ается в тот же слот зоны.
  3. Оставшийся dangling knote указывает на освобождённый слот. Когда ядро
     доставляет событие, filt_aioprocess() проходит по ЗАВИСНУТОЙ записи и
     кладёт в kevent её поля:
         kev.ext[0] = entry->errorval   (+0x28)
         kev.ext[1] = entry->returnval  (+0x20)
         kev.ident   = entry->uaiocbp    (+0x48)
         kev.udata   = aiocb->sival_ptr (+0x50)
     => ЧТЕНИЕ ПАМЯТИ ЯДРА ИЗ ПРИЛОЖЕНИЯ ПОДТВЕРЖДЕНО (это и есть B12-read).

  ЧТО ИМЕННО ДАЁТ UAF СЕЙЧАС (важно, без преувеличений)
  ---------------------------------------------------------------------------
  Реально подтверждено: kevent ДОСТАВЛЯЕТСЯ на освобождённую запись.
  Это UAF, а не «произвольное чтение ядра»:
    kev.ext[0] = слот+0x28, kev.ext[1] = слот+0x20,
    kev.ident  = слот+0x48, kev.udata  = слот+0x50
  Сейчас в слоте лежит ЛИБО обнулённая память (free обнуляет зону),
  ЛИБО донорная aio-запись (её поля — наши собственные значения).
  => значения ext[0]/ext[1] сейчас = наши же числа, т.е. это ПОДТВЕРЖДЕНИЕ
     UAF (маркер RECL_NB всплывает наружу), а не утечка чужих kernel-данных.
  Чтобы читать ЧУЖИЕ kernel-указатели, слот должен содержать объект
  ДРУГОГО типа, у которого на +0x20/+0x28 лежат указатели => нужен спрей
  в ту же зону/размер.

  ЗАПИСЬ (условие, а не «уже готовый write»)
  ---------------------------------------------------------------------------
  filt_aioprocess() на ЗАВИСНУТОЙ записи делает ровно три опасных действия:

      (a) TAILQ_REMOVE(entry)              -> *prev = next
          пишет по адресу, взятому ИЗ САМОЙ ЗАПИСИ (+0x10/+0x18).
          Сейчас «мёртво», потому что слот обнулён на free -> писать некуда.

      (b) aio_entry_unref(entry)           -> unref(+0x2C)
          refcount берётся ИЗ ЗАПИСИ. Если подсунуть 0/1 -> повторный free
          той же записи = DOUBLE FREE в зоне aio_workq_zonep.

      (c) aio_proc_lock(*(entry+0x40))    -> procp
          procp тоже ИЗ ЗАПИСИ. В заблокированном слоте он = 0 ->
          PANIC FAR=0x58 (это и есть наблюдаемый ребут в логах).

  КЛЮЧЕВАЯ МЫСЛЬ: (a),(b),(c) — это запись/чтение ЧЕРЕЗ ДАННЫЕ ЗАПИСИ.
  Если в слот вернуть СВОЙ КОНТРОЛИРУЕМЫЙ ОБЪЕКТ (а не обнулённую запись),
  то:
      (a) превращается в ЗАПИСЬ ПО АДРЕСУ И ПРОИЗВОЛЬНОМУ ЗНАЧЕНИЮ
          (write-what-where, значение = next/prev из нашего объекта);
      (b) превращается в DOUBLE FREE -> отравление freelist зоны
          -> выделение своего объекта поверх -> подмена указателя/колбэка;
      (c) procp из нашего объекта -> паника уходит (FAR=0x58 больше не будет).

  ЧТО НУЖНО ДОДЕЛАТЬ (всё в этом репозитории, device-итерации):
    A0. РАЗМЕЧИТЬ ТИПЫ В ЗОНЕ aio_workq_zonep (224 B / 0xE0): нужен СОСЕД,
        чьи +0x10/+0x18/+0x2C/+0x40 контролируемы. Это и есть
        «cross-type reclaim» линия B12/T3, которую проект ранее закрыл
        для 192-бакета — но для 224-бакета aio-зоны проверка не делалась.
    A.  Спрей в ЭТУ зону объектами нашего содержимого, чтобы свободный слот
        переиспользовался ДО обработки dangling knote. Текущий nk_spray.m —
        портовый спрей (E1, mach ports); порты аллоцируются в СВОЕЙ зоне,
        aio_workq_zonep они не трогают => нужен свой zone-спрей.
    B. Свой aiocb с aio_buf, заполненным заранее (our fake entry layout:
       +0x10 prev, +0x18 next, +0x20 returnval, +0x28 errorval,
       +0x2C refcount=1, +0x40 procp=NULL-safe, +0x48 uaiocbp).
    C. Повторная доставка события (второй knote на тот же слот, либо
       повторный kevent64) -> (a)+(b)+(c) отработают по нашим данным.
    D. После (a): write-what-where. Цели — writable function pointer в
       kernel data, или ucred->cr_uid (cr_posix+0x18 в kernel-layout
       struct ucred; в userspace-виде struct ucred без BSD_KERNEL_PRIVATE
       cr_posix тоже начинается с 0x18 -> uid @ ucred+0x18).
    E. После double-free: спрей в ту же зону -> контролируемый объект
       поверх -> подмена vtable/callback -> code exec -> kernel R/W.

  ПОЧЕМУ ЭТО САМЫЙ ДЁШЕВЫЙ ПУТЬ:
    - UAF-доказана на устройстве (не гипотеза);
    - read-канал работает и уже пишет kernel-данные в kevent;
    - запись не требует нового CVE, нового кекста, нового энтрипоинта —
      нужен только спрей в известную зону;
    - WebKit-pivot (renderer RCE) уже работает и даёт native-код в
      песочнице — он нужен, чтобы дотянуться до не-песочничных
      user-client'ов позже, но не для самого AIO-примитива.

  ТЕКУЩЕЕ СОСТОЯНИЕ В РЕПО:
    Sources/Legacy/aio_kevent_rw.c   — B1 (детерминированный триггер) + B2 (разведка)
    (кнопка «AIO UAF» = nk_aio_uaf_run)
    Sources/Legacy/aio_kevent_rw.h   — карта объекта aio_workq_entry (B0)
    Sources/Legacy/nk_spray.m        — портовый спрей (нужен zone-спрей для aio)
    Sources/Legacy/privesc.c         — nk_escalate_root (uid/gid -> 0)
    Sources/Kernel/b12_offsets.h      — offset-ы слота 192 B (устаревшие, см. B0 выше)

  ТЕКУЩИЙ СТАТУС: UAF + доставка kevent на освобождённую запись — [подтверждено
  на устройстве]. Произвольное чтение и запись — НЕ подтверждены: требуется
  сосед по зоне aio_workq_zonep с контролируемыми +0x10/+0x18 (пункт A0).
  Т.е. запись здесь НЕ бесплатна: это тот же cross-type reclaim, который
  проект закрыл для 192-бакета, но который НЕ проверялся для 224-бакета aio.

--------------------------------------------------------------------------------
 2.1  AIO KEVENT UAF  (трек B / «B12») — xnu bsd/kern/vfs/aio.c
--------------------------------------------------------------------------------
  Статус:  [R] read подтверждён на устройстве / [R/W] write требует zone-спрея
  Тип:     use-after-free в filt_aioprocess() (kevent-доставка на освобождённую
           aio_workq_entry), + double-free через aio_entry_unref.
  Доступ:  да, из обычного sandbox-приложения (aio_read + kqueue + kevent64).
  Публично: нет публичного CVE на этот конкретный вектор.

  Подтверждённые на device факты (Documents/aio_uaf.log):
    - knote доставляет событие на ЗАВИСНУТУЮ запись (HIT, слот занят спреем)
    - kev.ext[0] = entry->errorval, kev.ext[1] = entry->returnval,
      kev.ident = entry->uaiocbp, kev.udata = aiocb->sival_ptr
    - при обнулённом слоте procp = 0 -> PANIC FAR=0x58 (наблюдаемый ребут)

  Что даёт: чтение произвольных 8 байт kernel-памяти за событие; при контроле
  содержимого слота — write-what-where + double-free -> kernel R/W.

 2.2  WebKit DFG TYPE CONFUSION  (трек W, «W-T0/W-T2»)
--------------------------------------------------------------------------------
  Статус:  [R/W] подтверждён на устройстве (renderer, в песочнице WebKit)
  Тип:     type confusion в DFG (MapIterationEntryKey-подобный узел) -> UAF в
           JIT/DFG -> AAR + AAW в адресном пространстве рендерера.
  Доступ:  да, через WebKit в обычном приложении.
  Публично: да, по публичным writeup'ам (node shape известен).

  Подтверждено: 9+ верифицированных прогонов W-T0, AAR/AAW-echo (W-T2) ок.
  Ценность: это renderer primitive. Дальше нужен либо WebKit->native pivot
  (W-T3, в работе), либо связка с 2.5 (sandbox escape) — тогда native-код
  вне песочницы, и дальше — IOKit-примитивы.

 2.3  CVE-2025-24257 — IOGPU IOGPUGroupMemory::init BITMAP UNDERFLOW
--------------------------------------------------------------------------------
  Статус:  [DEAD] на 26.2 — недостижимо с userspace.
  Тип:     obj+40 = (capacity>>6)-1 без проверки capacity >= 64
           (0x9f612a4), маска используется как индекс бакетов.

  Что установлено (исправляет прежние выводы в этом репо):
    - Настоящая dispatch-таблица IOGPUFamily: 0xfffffff007e67c58, stride 0x18.
      Это ДВЕ 56-элементные таблицы подряд, а не одна на 112.
      Type 1 -> таблица A (0..55); type 33 -> A+B (0..127).
      AGXG14P type=1 -> 0x7b3d900, всего 19 селекторов (0..18).
    - Селектора 64 в таблице IOGPUFamily type=1 НЕТ (это был ложный след
      из blocks-скана; указателей на 0x9f541ec нет ни в кексте, ни в ядре,
      ни как chained, и у функции нет ни одного bl-вызова).
    - Группа создаётся селектором 8 на type=1: struct[0]=3 (resType=group),
      struct[56]=capacity, out+0x10 = указатель на группу.
      capacity обязан быть степенью двойки >= 64; при capacity < 64 ->
      kIOReturnNoResources (underflow-маска 0xffffffff делает аллокацию
      невозможной) — то есть путь закрыт, а не открыт.
    - init (0x9f61200) вызывается РОВНО из двух мест, оба через bti-pad
      0x9f611ec:
        * 0x9f610cc — из 0x9f60fcc, где стоит гейт `cmp w2,#0x3f; b.hi`
          (capacity > 63). Этот путь user-client-достижим (sel 8) и ЗАЩИЩЁН.
        * 0x9f649ac — grow-путь, capacity = 2*[x0+32], БЕЗ нижней границы.
          Сам grow (0x9f64910) зовётся из 0x9f62ed4/0x9f63848, а их владелец
          (0x9f62b3c) не имеет прямых callers => только через vtable.
      ИТОГ: баг ЖИВ (одна точка входа не защищена), но из user-client селектора
      недостижим — ровно как и задумано в исходном выводе проекта (§4.4.9).
      Прежний вывод был ВЕРЕН, неверным было только его ОБЪЯСНЕНИЕ
      (искали sel 11/64 в неверной таблице).

  Итог: CVE-2025-24257 в 26.2 закрыт (Apple пофиксила в 18.4 — проверка
  `cmp w2,#0x3f` в 0x9f60fcc есть в 23C55). Линия закрыта.

 2.6  vm_fault_copy (RE)TYPE RACE  (найдено в исходниках, не в advisory)
--------------------------------------------------------------------------------
  Статус:  [DEAD] — 26.2 не эксплуатируем
  Тип:     в xnu-61.12 SPTM-pmap есть гонка с re-type; в xnu-12377.81.4
           (26.3) закрыта. На 26.2 SPTM-апёрт делает память физически
           write-protected, поэтому гонка даёт panic-DoS, а не запись.

  Связанная находка (этот репо): SPTM-бинарь 23C55 доступен оффлайн и
  разобран — Firmware/sptm.t8110.release.im4w НЕ зашифрован (в отличие от
  sep-firmware, где ключ от устройства). Полная карта SPTM (FTE layout,
  матрица 64 типов, адреса функций) — в Docs/sptm_23c55.md.
  Найденный кандидат S1: pmap_recycle_page() делает три НЕАТОМАРНЫХ вызова
  SPTM (is_page_free / get_frame_type / retype), возврат retype игнорируется,
  а SPTM отклоняет retype при несовпадении типа => кадр уходит в free-list
  с типом != XNU_DEFAULT. Это «липкий тип кадра» — но на 26.2 проверка
  `cmp w2,#0x3f` в 0x9f60fcc закрывает путь через newResourceGroup.

Что делает:
  * открывает 8 сервисов (IOGPU, IOGPUDevice, AGXG14P, IOGPUDeviceUserClient,
    AppleDCP, IOAccelDevice, IOAccelShared, IOSurfaceRoot) x 8 типов
    (1,2,5,33,3,4,6,0);
  * для каждого селектора 0..127 и каждого u32-слота struct'а (0x400 байт)
    подставляет count/size-класс значений:
        0xffffffff 0x7fffffff 0x10000000 0x1000000 0x10000 0x80000000
        0xffff0000 0x0000ffff 0x100000000 0x1000 16 0xffff
  * ПЕРЕД КАЖДЫМ вызовом пишет durable-строку
        [hunt] CALL <svc> type=<t> sel=<n> off=0x<o> val=0x<..>
    поэтому после ребута последняя строка лога называет ТОЧНЫЙ вызов,
    который убил ядро.

Почему значения только count/size-класса: poison-указатели дают ложные
паники (любой метод просто разыменует мусор) — это не уязвимость, а наш
собственный краш. Нас интересует только значение, ломающее ПРОВЕРКУ ГРАНИЦ.

Ограничения (честно):
  * нет гейта по arity -> часть вызовов отбивается bad-argument; это нормально,
    отсеивается по коду возврата;
  * паника ядра = наш баг только если она воспроизводима и её видно в
    device panic log (FAR/PC), а не только в oob_hunt.log;
  * 40 000 вызовов на прогон, 300 мс пауза — watchdog-safe.

8.15 ИСПРАВЛЕНИЕ: МАТРИЦА cmd=64 БЫЛА СЛОМАНА (мой баг, не свойство билда)

В 8.13 я закрыл cmd=64 выводом "cmd=64 мёртв - NoResources на всех

состояния СЕССИИ до всей работы:

  0x9f61354: tbnz w8, #1 -> fail
Создание группы этот бит ставит, поэтому cmd=64 всегда приходил в
испорченную сессию. Отказ был артефактом теста.

Новые фазы (исправлены):
  K: cmd=64 на СВЕЖЕЙ сессии (без cmd=3 впереди), dim in {1..65536}, cap=1
  L: cmd=64 свежая сессия, dim=1, cap in {1,2,3,4,8,16,32,63,64,128,256}

ТРИГГЕР (кнопка "Group OOB (cmd64 cap=1)", trigger=2):
  1. cmd=64 с struct[56]=1 (capacity), struct[80]=1 (dim) - округление
     (cap+dim-1) & -dim не меняет capacity, значит capacity == 1.
  2. capacity == 1 => log2(capacity) == 0 => lsr x9,x20,x9 в 0x9f62c04
     вырождается в сдвиг на 0 => bucket = полный 64-битный хеш =>

8.16 ГЛАВНАЯ МОЯ ОШИБКА: ДЕСЯТИЧНЫЕ СМЕЩЕНИЯ ЧИТАЛ КАК ХЕКС

  ldr w8, [x0, #40]  это 0x28, а НЕ 0x40

Из-за этого я неверно привязал slot table к смещению +0x40 и строил
выводы на неверной карте. Правильная карта slot table (0x9f518ac):
  +0x10 массив (элемент 8 байт)
  +0x18 bitmap
  +0x28 capacity
  +0x2c cap-1
  +0x30 MASK
  +0x34 log2
и РMW bitmap (0x9f51904) НЕ МАСКИРУЕТ индекс (w1>>6) - защита только
index < capacity.

ЖИВОЙ 24257 НА 23.55 (новая форма):
  0x9f51914: ldr  w9, [x0, #48]   ; +0x30 = MASK
  0x9f51918: sub  w9, w9, #1      ; МАСКА ДЕКРЕМЕНТИРУЕТСЯ
  0x9f5191c: str  w9, [x0, #48]
Группа с capacity 64 имеет MASK = (64>>6)-1 = 0. ПЕРВОЕ ЖЕ УДАЛЕНИЕ
ресурса превращает маску в 0xffffffff. После этого индекс bitmap не
маскируется, и insert (0x9f62c04 lsr x9,x20,x9 -> 0x9f62c28 ldr w10,[x12]
-> bic/str) выходит за аллокацию. 4-байтный RMW по хеш-смещению.

ТРИГГЕР (trigger=3, кнопка "Group OOB (путь удаления)"):
  1. cmd=3 type=64 -> группа (capacity 64, MASK=0)
  2. cmd=130 с global id поверхности -> ресурс добавлен
  3. перебор всех команд 0..255 с ключом = global id (и с хендлом группы)
     -> ищем команду удаления (kr=0)
  4. удаляем -> MASK становится 0xffffffff
  5. cmd=130 снова -> insert с испорченной маской = OOB

Также исправлено чтение grow: цикл 0x9f64940 выполняется ДВАЖДЫ
(mov x21,x8 пере-исполняется), поэтому новая capacity = 2*старая, а не
старая. И grow хеш-таблицы (0x9f7699c) берёт capacity из +0x28 и новая
capacity = w1 (явная, от вызывающего) либо 2*старая; единственный вызов с
w1 != 0 считает w1 = count + (count>>2) = count*5/4 (0x9f7588c) - при

маска портится" работает, и запись в bitmap уходит за пределы
аллокации, попадая в отображённую память (паники нет).

ЧТО ОСТАЁТСЯ ПРОВЕРИТЬ (и почему паники не было):
  индекс слова bitmap = (bucket >> 6) & MASK (0x9f63148/0x9f6314c).
  bucket = hash >> (64 - log2(capacity)), т.е. bucket < capacity.
  При capacity = 64 bucket <= 63 => bucket>>6 = 0 => индекс ВСЕГДА 0,
  то есть запись попадает в сам bitmap, а не за него.
  => чтобы индекс стал ненулевым, нужен capacity > 64 (тогда bucket>>6
  может быть 1) при СЛОМАННОЙ маске, либо capacity == 1 (log2 = 0 ->
  сдвиг вырождается -> bucket = полный хеш -> индекс огромный).

СЛЕДУЮЩИЙ ШАГ - ИНДЕКС-СВИП (trigger=5, кнопка "OOB: свип индекса"):
  remove хеш-таблицы (0x9f518ac) берёт элемент по индексу с шагом 8
  байт (ubfiz x9,x1,#3) из массива +0x10, который аллоцирован как
  kalloc(capacity*4) - 4 байта на слот. Единственная проверка -
  "index < capacity" (0x9f518b4). Значит индекс в [capacity/2, capacity)
  пишет 8 байт за конец массива (0x9f518f0 str xzr,[x10]).
  Свип по индексам 0..256 по всем командам: если клиент умрёт -
  OOB попал в неотображённую страницу, это подтверждение.

КНОПКИ УБРАНЫ: остались "OOB: дубль-insert (зажиг)", "OOB: свип индекса",
"Охота за утечкой ядра", "NECP цепочка (чтение)", "Матрица capacity".
Мёртвые режимы (cmd64 cap=1, путь удаления, старый триггер) удалены.


8.21 ЧТЕНИЕ ЯДРА: ДЕТЕКТОР БЫЛ СЛЕП К PAC + КНОПКА ОТОБРАЖЕНИЯ

Детектор утечки сравнивал сырое значение с 0xfffffff000000000. На arm64e
IOKit-метод, возвращающий OSObject*, отдаёт PAC-подписанный указатель:
адрес в младших 56 битах, PAC-код в старших. Сырое значение никогда не
попадало в диапазон => ВСЕ утечки были пропущены. Теперь PAC маскируется
(KL_PAC_MASK 0x00ffffffffffffff) в kern_leak_hunt.c и oob_hunt.c.

Новая кнопка "Kernel map (утечка -> отображение)": берёт сохранённые
хиты и пытается превратить kernel pointer в отображение:
  IOMemoryDescriptorGetAddress(ptr) -> userspace-адрес kernel-памяти
  IOMemoryDescriptorGetLength(ptr) -> размер
и дампит 256 байт. Это полное чтение ядра без всякого WebKit.
Аксессоры IOMemoryDescriptor* не объявлены в iOS-SDK (только macOS),
поэтому объявлены weak вручную - если символа нет, отчёт пишется в лог
вместо падения.

ПЛАН СОВМЕСТНО С WEBKIT:
  1) kernel pointer в userspace-памяти (из утечки user client'а);
  2) рендерный AAR/AWW (уже подтверждён) читает/пишет по этому адресу
     => kernel read/write из процесса рендера;
  3) либо отображение IOMemoryDescriptor => чтение напрямую из нашего
     процесса, а OOB-запись IOGPU даёт запись.
Схема "рендерный AAR/AWW + OOB" требует kernel pointer в памяти
рендера: он берётся из XPC-ответа или из той же утечки.


8.22 ОБХОД РЕЕСТРА: IORegistryEntryCreateIterator + IOIteratorNext

Прогон 19:01 снова оборвался на "named phase conns=15" без строки
"registry walk" - то есть старая сборка, а новая падала/зависала на самом
вызове IOServiceGetMatchingServices(NULL): он материализует ВСЕ службы
сразу, и телефон замирает.

Правильный API для iOS (тот, что документирован в iOS-SDK):
  IORegistryEntryCreateIterator(kIOMasterPortDefault, kIOServicePlane,
                               kIORegistryIterateRecursively, &iter)
  + IOIteratorNext(iter)
- IORegistryCreateIterator в iOS-SDK нет, а его итератор не является
  обычным io_iterator_t, поэтому IOIteratorNext на нём даёт 0.
- IOServiceMatching(NULL) непригоден: он разворачивает весь список
  служб сразу => ступор телефона.
Добавлен жёсткий бюджет времени (20 с) и лимит 300 записей, usleep
каждые 20 открытий.

СВЯЗКА С WEBKIT-ООБ (ответ на вопрос):
  Рендерный AAR/AWW даёт произвольные读写 в адресном пространстве
  РЕНДЕРА. Kernel pointer в этом пространстве - единственный мост к
  ядру. Наш OOB - это запись в ЯДРЕ. Связать можно так:
  1) kernel pointer попадает в память рендера (из XPC-ответа или из
     утечки user client'а) => рендерный AAR/AWW = kernel R/W;
  2) OOB-запись целится в объект, наблюдаемый из рендера (XPC-буфер,
     mach-порт, общая память) => рендер читает испорченный объект;
  3) рендерный AAR/AWW подделывает XPC-сообщение приложению, и
     приложение выполняет IOGPU-OOB с управляемыми параметрами.
  РУЧКА ПРИЦЕЛИВАНИЯ: смещение OOB = (hash>>6)*8, где
  hash = [resource+0x70] * 0x9e3779b97f4a7c15, а resource - это
  IOSurface. Значит, меняя свойства IOSurface, мы меняем хеш и,
  следовательно, смещение записи. Какой именно ключ IOSurface попадает
  в resource+0x70 - надо найти перебором (краш как оракул).

8.24 AIO KEVENT UAF - ЖИВОЙ CVE НА 26.2, ГДЕ ИМЕННО УТЕКАЕТ УКАЗАТЕЛЬ

hunt/aiouaf/aio_kevent_uaf.m (донор-PoC) прямо пишет:
  Affected: iOS 26.2 (xnu-12377.62.10) and earlier
  Fixed:    iOS 26.3 (xnu-12377.81.4)
  Impact:   kernel panic from app sandbox, no entitlements
  Success:  ~70% (CPU-affinity LIFO reclaim)
Корень: lio_listio() регистрирует kevent ПОСЛЕ постановки AIO-работы
=> гонка с aio_return() => dangling knote => filt_aioprocess() на
освобождённой записи => double-free через aio_entry_unref().

ГДЕ УТЕКАЕТ УКАЗАТЕЛЬ:
  filt_aioprocess пишет ТОЛЬКО ext[0] (=entry+0x28, errorval) и
  ext[1] (=entry+0x20, returnval). ext[2]/ext[3] он НЕ трогает - там
  остаётся мусор из буфера kevent в ядре, то есть хвост стека ядра:
  возвращаемые адреса, frame pointers. Это и есть кандидат на якорь
  KASLR. До сих пор ext2/ext3 только сканировались на kernel VA, но не
  печатались - теперь печатаются всегда.
  Плюс итоговая сводка: "[AIO-B12] KVA hits=N best_field=... best=0x...".

Второй канал - double-free: после filt_aioprocess unref'а dangling
записи освобождается reclaimed-запись, а её содержимое = aio_workq_entry
с kernel-указателями на +0x38 (lio_leader) и +0x40 (procp). Освобождённый
чанк уходит в freelist с этими указателями - если его переиспользует
kernel-объект, чтение его полей даст настоящий kernel VA.

СЛЕДУЮЩИЕ ШАГИ (после первого прогона):
  1) если ext2/ext3 дают kernel VA - это якорь KASLR; дальше считаем
     base = value - (unslid адрес функции) и получаем kernel read/write;
  2) если нет - поднимаем hit-rate: донор-PoC использует NRECLAIM=8
     reclaim-слотов (у нас один), и добавляем double-free-канал.

8.28 НАСТОЯЩАЯ ПРИЧИНА ПАНИКИ: CPU-ПИННИНГ + МАРКЕР БОЛЬШЕ ФАЙЛА

Донор-PoC пиннит main-тред И рацер на ОДИН CPU (set_thread_affinity(42)):
тогда free и reclaim попадают в magazine одного CPU, и LIFO даёт точный
reclaim освобождённого слота. Мой комментарий "LIFO-reclaim не требует
пиннинга" был неправильным: между free и reclaim тред успевает мигри-
ровать, reclaim забирает чужой слот, освобождённый слот остаётся
обнулённым, filt_aioprocess читает procp == 0 -> PANIC FAR=0x58.
Исправлено: aio_set_affinity() через thread_policy_set(THREAD_AFFINITY_POLICY)
на рацере и на main-треде (тег 0).

Вторая ошибка: маркер 0x4141 = 16641 байт, а файл был 4096 байт. reclaim
читает aio_nbytes байт, ядро кладёт в returnval ФАКТИЧЕСКИ перенесённое
число байт - то есть 4096, а не маркер. Проверка HIT всегда проваливалась.
Исправлено: файл 0x10000 байт (буферы жертвы/ reclaim'ов тоже), маркер
0x4141 теперь читается целиком.

Итог: ждём завершения reclaim-I/O перед kevent64, слот занят нашей
записью, фильтр копирует ext[1] = 0x4141 наружу = HIT без паники.


8.29 ПОИСК СВОИХ УЯЗВИМОСТЕЙ В 23C55

A) Регресс-скан "Apple удалила проверку" (18.x 23A355 -> 26.2 23C55).
   22 кекста в обоих дизасмах, сопоставление функций по прологу,
   сравнение числа "cmp + условный переход". РЕЗУЛЬТАТ: 0 - ни одна
   функция не потеряла граничную проверку. Лёгкой регрессии Apple в
   этих кекстах нет.
   Скрипт: /tmp/kilo/regress_check2.py (перенос в Tools/regress/).

B) Поиск "user-controlled length -> copy" в кекстах 23C55: вызовы
   memcpy/bcopy/memmove в дизасме не находятся (llvm-objdump по rawslice
   не печатает имена, вызовы идут через стабы) - нужен разбор стабов
   или Capstone по Mach-O.

C) Основной инструмент: OOB hunt v2 (arity-correct) - таблицы арности
   взяты из реальных dispatch-таблиц 23C55, поэтому каждый метод
   вызывается в той форме, которую он ждёт. Кнопка "OOB hunt v2"
   возвращена в UI.

D) Логи: C-сторона теперь пишет СРАЗУ в каталог, который передаёт
   Swift (реальный Documents приложения - тот, что виден в "Файлах"),
   а не в remap'нутый guest-home. nk_doc_log_set_visible_dir().


8.30 УПРАВЛЯЕМАЯ OOB-ЗАПИСЬ: ИНДЕКС РУЛИМ ЧЕРЕЗ СВОЙСТВА IOSurface

Статический разбор remove из хеш-таблицы (0x9f518ac):
  0x9f518b0: ldr  w8, [x0, #40]      ; capacity
  0x9f518b4: cmp  w8, w1
  0x9f518b8: b.ls fail               ; единственная защита: index < capacity
  0x9f518d0: ubfiz x9, x1, #3        ; индекс*8  (шаг 8 байт)
  0x9f518ec: ldr  x8, [x10]
  0x9f518f0: str  xzr, [x10]         ; запись 8 нулевых байт
Массив элементов по +0x10 аллоцирован как kalloc(capacity*4) - 4 БАЙТА на
слот, а обращение идёт с шагом 8 байт. При capacity=64 массив 256 байт,
индекс >= 32 => запись за конец.

Индекс элемента = (bit + bucket) & (capacity-1), а bucket берётся из
hash = [resource+0x70] * 0x9e3779b97f4a7c15 - то есть из поля IOSurface.
Смена свойств поверхности меняет хеш => рулим индексом => рулим смещением
записи (0..248 байт за 256-байтовую kernel-аллокацию).

Дубль-insert и есть то, что вызывает remove: вставка находит старую
запись и выбрасывает её.

Пробник trigger=6, кнопка "OOB запись (рулим индексом)": 20 геометрий
поверхности (16x16..4096x4096, bpe 1/2/4/8/16), для каждой - своя группа,
add #1 и add #2 (тот же id). Лог: id, add1, add2; смерть клиента = OOB
запись попала в значимое место.


8.31 ГРУППА ОТДАЁТСЯ В USERSpace - ЕЁ МОЖНО ПРОЧИТАТЬ БЕЗ KERNEL-READ

Из лога 21:24: STEP 2 group ptr = 0x0000000120256dc0 - userspace-адрес.
Пробник читал его через мёртвый kernel-read канал (STEP 4 kread -> -1), но
для userspace-адреса он не нужен: обычный memcpy делает это сам.

Добавлен grp_safe_read(): прямой memcpy под защитным SIGSEGV-обработчиком
(sigsetjmp/siglongjmp), с откатом на чтение по 0x20, если отображена
только голова объекта. grp_dump_handle() выводит все ненулевые 8-байтные
поля объекта и помечает kernel-адреса (с маской PAC).

Если объект отображён - получаем внутренности группы: element array,
bitmap и MASK, а указатели на массив/bitmap - это ЯДЕРНЫЕ АДРЕСА. Это и
якорь KASLR, и readback, которого не хватало для проверки всего
остального. Тот же механизм даёт прямое чтение MASK - значит можно
ПОДТВЕРДИТЬ, что маска уехала в 0xffffffff после дубль-insert.

Результат свипа 21:24 (trigger=6): 20 геометрий, все add1/add2 = 0x0,
смертей нет - OOB-запись (если была) попала в безобидную память.


8.32 ЧТЕНИЕ ХЕНДЛА РАБОТАЕТ, НО ЭТО ОБЩИЙ БУФЕР

Прогон 21:29: grp_safe_read() отработал - страница отображённая, SIGSEGV
не случился. Но содержимое НЕ структура группы: все поля с +0x08
содержат повторяющийся паттерн 0x000000ff000000ff, первые 8 байт нули.
=> out+0x10 - указатель на userspace-разделяемый буфер (заливка), а не на
kernel-объект группы. Kernel-указателей там нет.

Дамп делался сразу после создания группы, ДО добавления ресурсов. Если
группа публикует своё состояние (element array, bitmap, MASK) в этот
буфер, оно появится после add. Пробник теперь дампит хендл трижды:
сразу после create, после add #1 и после add #2. Сравнение дампов
покажет, что именно группа туда пишет - и если там окажется MASK или
указатели на element array/bitmap, это и есть якорь KASLR плюс
readback для подтверждения OOB.
